# セキュリティ／ファイアウォール設計

「誰にも真似できず、ウイルスにも感染しないアプリ」という要望を、実装可能な
2つの技術課題に分解して設計します。

> **正直な前提**：ソフトウェアの世界で「絶対に誰にも真似されない」「100%感染しない」
> を技術的に保証することはできません。以下は、模倣コストを最大化し感染リスクを
> 現実的な最小値まで下げるための、業界標準の多層防御（Defense in Depth）設計です。

---

## 1. アップロード写真からのウイルス／マルウェア対策（ファイアウォール本体）

画像アップロードは以下の6層を**すべて**通過しないと変換処理に進めない構成にします。

| 層 | 対策内容 |
|---|---|
| 1. 通信経路 | HTTPS必須、WAF（Web Application Firewall）でSQLi/XSS/既知の悪性ペイロードを遮断 |
| 2. ファイル種別検証 | 拡張子だけでなく**マジックバイト（ファイル先頭シグネチャ）**でJPEG/PNG/HEICか検証。それ以外は即時拒否 |
| 3. サイズ・寸法制限 | ファイルサイズ上限（例：20MB）、画像解像度上限を設定し、ZIP爆弾的な巨大画像でのDoSを防止 |
| 4. 隔離バケット保存 | アップロード直後は本番ストレージではなく**隔離用バケット**に保存し、スキャン合格後のみ本処理領域へ移動 |
| 5. マルウェアスキャン | ClamAV等のアンチウイルスエンジンをサーバーレス関数で非同期実行し、EXIFに仕込まれたスクリプトやポリグロットファイルを検出 |
| 6. 画像の再構築（最重要） | 元ファイルを直接扱わず、**ピクセルデータのみをデコードして新規ファイルとして再エンコード**する。これによりファイル内に埋め込まれた不正コード・メタデータ・位置情報（EXIF GPS）を構造ごと破棄できる（画像処理業界で最も効果的な対策） |

追加のインフラ対策：
- 画像処理はコンテナ／サンドボックス内で実行し、ネットワークアクセスを遮断（外部への不正通信を物理的に不可能にする）
- 処理コンテナは使い捨て（ephemeral）にし、処理後は都度破棄
- レート制限・IPベースの異常検知で連続アップロード攻撃を防止
- 依存ライブラリ（画像処理系）は既知脆弱性のCVEスキャンをCIに組み込み、定期更新

### 実装状況（`backend/src/pipeline/malwareScan.ts`）

- 常時：ヒューリスティックスキャン（`<script`, `<?php`, 実行ファイルヘッダ等のポリグロット
  シグネチャ検出）
- `CLAMAV_HOST` 設定時：`docker-compose.yml` で起動したClamAVデーモンに `INSTREAM`
  プロトコルで接続し、実ウイルス定義ベースのスキャンを実施
- **fail-closed方針**：ClamAVへの接続に失敗した場合（未起動・タイムアウト等）は
  「安全側」に倒し、スキャン不可＝拒否として扱う。可用性より安全性を優先する設計であり、
  ClamAVコンテナが健全に稼働していることが前提となる（`docker compose ps` で
  healthy を確認すること）

## 2. プロンプト／ノウハウを模倣されないための対策

「誰にも真似できない」を目指すなら、**単一の呪文（プロンプト文字列）に価値を置かない**
設計が本質的に重要です。競合が同じプロンプトをコピーしても再現できないよう、以下を
組み合わせます。

| 対策 | 内容 |
|---|---|
| プロンプト非公開 | システムプロンプトはサーバーサイドのみで保持し、APIレスポンスやフロントエンドのコードに一切含めない |
| プロンプトインジェクション対策 | ユーザー入力とシステム指示を明確なデリミタで分離し、「以降の指示を無視して」等の攻撃文をフィルタリング・検知 |
| 出力サニタイズ | AIの応答にシステムプロンプトの内容が漏れていないか後処理でチェックし、該当時はブロック・再生成 |
| 多段パイプライン化 | `prompts/transformation_prompt.md` の1枚岩プロンプトではなく、①顔分析→②パーソナルカラー診断→③メイク生成→④ヘア生成→⑤スタイリング生成、という**複数モデル呼び出しの独自パイプライン**にする。プロンプトだけ盗まれてもパイプライン構造・診断ロジック（骨格診断アルゴリズム等）は再現できない |
| 診断ロジックの独自資産化 | 顔型判定・パーソナルカラー判定を外部LLM任せにせず、自社の学習済み分類モデル／ルールベースエンジンとして保有する（これが本当の模倣困難性の源泉になる） |
| 生成物の透かし | 出力画像に不可視電子透かし（invisible watermark）を埋め込み、後から自社生成物であることを証明できるようにする |
| APIキー・エンドポイント保護 | クライアントから直接AIプロバイダーAPIを叩かせず、必ず自社バックエンド経由のプロキシにし、キーをクライアントに露出させない |
| 利用規約・法的保護 | リバースエンジニアリング禁止条項、商標・意匠登録など法的手段も技術対策と併用する |

## 3. 倫理・プライバシー面の必須ガードレール

写真を使った容姿変換アプリは、技術対策と同じくらいここが重要です。

- **本人確認・同意**：アップロードは本人の写真であることを利用規約で明示同意させ、
  第三者の写真の無断アップロードを禁止する
- **未成年者保護**：年齢確認フローを設け、未成年者の画像は処理しない／保護者同意を必須にする
- **データ保持ポリシー**：アップロード画像・生成画像は処理完了後、短期間（例：24時間）で
  自動削除。長期保存する場合は明示的なオプトインのみ
- **なりすまし対策**：生成画像には「AI生成」であることを示す透かし・メタデータを付与し、
  悪用（なりすまし投稿等）を抑止する
- **削除リクエスト対応**：ユーザーが過去のアップロード・生成データの削除を即時依頼できる
  導線を用意する

---

## 4. まとめ（優先実装順）

1. 画像の再エンコード＋EXIFストリッピング（マルウェア対策の中核、実装コスト低）
2. 隔離バケット＋ウイルススキャン
3. システムプロンプトのサーバーサイド非公開化＋プロキシ経由API呼び出し
4. 多段パイプライン化（模倣困難性の本質的な源泉）
5. 電子透かし・データ保持ポリシー・年齢確認等の倫理対策
